- [ ] **7.1 Scalable mutation testing in CI.** `task/7.1-scalable-mutants` — human request 2026-09-25. Today `ci.yml` runs one `mutants` job (`cargo mutants -j 2 --timeout 120 --in-diff`), so its time grows linearly with the change: the Stage 6 integration branch (292 mutants) took ~50 min, and a large feature could take hours or days. Goal: a wall-clock time close to constant whatever the size of the change, **without weakening the gate** (every mutant of the diff is still tested before the merge; no `--iterate`, no sampling, no skips). Research: https://mutants.rs/shards.html, /performance.html, /nextest.html, /in-diff.html, /iterate.html.
  1. **Shards sized by the diff.** A first short job computes the diff against the merge base (as today) and counts its mutants (`cargo mutants --list --in-diff <diff>`); it outputs a dynamic GitHub Actions matrix of `n` shards (about one shard per 25 mutants, at least 1, at most 20 — the free plan's concurrent-job limit for a public repo; `n` = 0 → the job is skipped). Each shard runs the **same** arguments with `--shard k/n --sharding round-robin` (identical arguments and denominator in every shard, or results are meaningless). A final job fails the check when any shard reports MISSED or TIMEOUT, and gathers the shards' `mutants.out` as one artifact.
  2. **Cheaper mutants.** (a) `test_tool = "nextest"` in `.cargo/mutants.toml` with a nextest profile that fails fast (the first failing test is enough to catch a mutant; today every mutant runs the whole suite, including the integration tests that start real daemons); check first that no mutant is caught only by a doctest (nextest does not run doctests). (b) `--baseline=skip` in the shards: the `rust` job already proved the suite passes (keep the `rust` job a required dependency of the shards). (c) A `[profile.mutants]` (inherits `test`, `debug = "none"`) passed with `--profile mutants`; the mold linker on CI (`.cargo/config.toml` for the linux target, or `RUSTFLAGS` in the job); `Swatinem/rust-cache` keyed per shard. (d) Replace the fixed `--timeout 120` with cargo-mutants' automatic timeout (a multiple of the measured test time; `--minimum-test-timeout` if needed), which avoids false TIMEOUTs such as `app_frame` on slow runners; revisit the `--test-threads=16` workaround from 6.99 (`additional_cargo_test_args`) once nextest is in.
  3. **Two levels.** Per branch (blocks the merge): only the diff's mutants, sharded (1–2). Nightly on `main` (scheduled `mutants-full.yml`, not blocking, also `workflow_dispatch`): every mutant of the workspace, sharded; a surviving mutant opens a GitHub issue with the list (covers `--in-diff`'s blind spot: a change can leave code outside the diff untested).
  Also keep `origin/main` up to date after each integration so each branch's diff holds only its own changes. Update `CLAUDE.md` (Quality gates), `.claude/skills/gates/` and `scripts/gates.sh` (local optional equivalent: same config, one shard) and `docs/architecture.md` if it describes CI. Tools installed in CI only (`cargo-nextest`, `mold`): not project dependencies. Measure before/after on the same diff (e.g. re-run the Stage 6 integration diff) and report the numbers. The human decides the shard size and cap if the defaults do not fit.
