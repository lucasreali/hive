# Hive architecture

The WSL side is the `hive` binary and the `hive-protocol` crate (Stage 0); the Windows side is the Tauri app (`src-tauri`) and its React UI (`src`).
Decisions live in `docs/hive.md` (Portuguese). This file describes how the code implements them.

## Pieces

```
Windows                         WSL
┌────────────┐  wsl.exe   ┌──────────────┐  Unix socket  ┌─────────────────────────────┐
│ Tauri app  │◄──stdio───►│ hive bridge  │◄─────────────►│ hive daemon                  │
└────────────┘  (frames)  └──────────────┘               │  terminals (PTY + fish)      │
                                                          │  hook events → app           │
             Claude Code in a Hive terminal               │  unhooked-claude watcher     │
             └─ hooks ─► hive hook <event> ──────────────►└─────────────────────────────┘
```

| Command | Role |
|---|---|
| `hive daemon` | The service. It owns the PTYs, receives hook events and lives exactly as long as the app connection. |
| `hive bridge` | stdio ↔ socket relay run by the app through `wsl.exe`. It starts the daemon when needed. |
| `hive hook <event> [--record FILE]` | Called by Claude Code hooks. Forwards one event and always exits 0. |
| `hive statusline` | Claude Code's `statusLine` in Hive's terminals: reports the 5-hour usage to the service, then runs the user's own statusline and prints what it prints (see [Session usage](#session-usage-121)). |
| `hive badge <text…>` / `hive badge --clear` | Run inside a Hive terminal: sets or clears that terminal's label on its tab and agent row. Exits 2 without a valid `HIVE_TERMINAL_ID`, 1 when the service cannot be reached. |
| `hive worktree create/list/remove/hook-create/hook-remove` | Worktrees following Claude's convention. |

## Wire protocol

Every message is a frame, big-endian: `[type: u8][channel: u32][length: u32][payload]`.

- **type** `0` = control: the payload is one JSON `Control` message, tagged by `"type"` in snake_case. **type** `1` = terminal: the payload is raw PTY bytes.
- **Contract (9.25).** The app's TypeScript mirror of the messages it receives is `ServiceMessage` in `src/protocol.ts`, reduced by `apply` in `src/reduce.ts`. `crates/hive-protocol/tests/app_messages.rs` writes one sample of every `Control` variant the app receives to `tests/app-messages.json` (checked in; the test rewrites it and fails when it was stale), and `src/protocol.test.ts` runs each through `apply` and checks that its type is known and its top-level fields are exactly the ones `ServiceMessage` gives it (plus what the Tauri pump adds: `channel`, and `app_*` and `bundled` on `version_mismatch`). A variant or field renamed, added or removed on one side fails the other's tests. The same test file sorts every variant into sent and received (an exhaustive match: a new variant does not compile until it is sorted), checks that every received one has a sample, and checks the [Message catalog](#message-catalog) below against the code (9.26): one row per `type`, none that no longer exists, each in the direction it is sorted into (a received one's ends at the app or a client).
- **channel** `0` is the connection itself. Channels from `1` up are terminals, and the channel number is also the terminal's `HIVE_TERMINAL_ID`.
- **Size limit.** The maximum payload is 4 MiB (`MAX_PAYLOAD`) in both directions. The decoder never panics: it fails with `Oversized`, `UnknownType` or `Json` errors. A message too big to encode never ends a connection: the app's Rust side refuses the command with the `Oversized` error (e.g. saving a huge paste), and the service's writer drops the frame with a warning in `daemon.log`.
- **Priority.** The service's writer always drains queued control frames before terminal frames. Terminal frames wait in one queue per terminal, and the writer takes the terminals in turn (channel order, wrapping), so a keystroke's echo waits for at most one frame of each other terminal.
- **Flow control (9.19).** The app acknowledges each terminal's output once xterm.js has written it (`ack {bytes}`). The service stops reading a terminal's PTY while more than 512 KiB of its output is unacknowledged (`terminal::HIGH_WATER`) and reads it again under 128 KiB (`LOW_WATER`), so a flooding program (`yes`, `cat` of a huge file) waits for the screen instead of growing memory in the service, Tauri or the webview, and each terminal's queue holds at most 512 KiB and one read (64 KiB). Tauri forwards terminal output without blocking; the acknowledgements are what bound it.

### Handshake

The first frame from every client is `Hello { protocol, version, role }`, where `role` is `app` or `hook`.
- If both `protocol` (`PROTOCOL_VERSION`) and `version` (the `hive` binary version) match, the service answers `Welcome { version, distro }`. `distro` is the service's `WSL_DISTRO_NAME` (null when unset), shown in the app's status bar: the service knows its distribution, so Windows never has to guess it from `wsl.exe`. It was added as an optional field (`#[serde(default)]`), which old decoders ignore and new decoders default, so `PROTOCOL_VERSION` stayed 1.
- Otherwise it answers `VersionMismatch { protocol, version }` with its own values and closes the connection. This is a hard error: the app must block and tell the user.
- Any other first message gets `Error` and the connection is closed.

Between the app's Rust side and the WebView (#24), control messages travel on one Tauri `Channel` (given by the `connect` command) as the service's JSON plus a `channel` field, e.g. `{"type":"terminal_opened","channel":1}`. Terminal output travels as raw bytes on a separate `Channel` per terminal (given by `open_terminal`). No Tauri events are used. The Rust side forwards each control payload as it came, reading only its `type` (it acts on `welcome`, `version_mismatch` and `terminal_exited` itself), so it never decodes a message it only passes on. A payload that is not JSON or has no string `type` is skipped with a line on stderr; the connection and its terminals stay up (only a broken frame ends it). The Rust side adds `app_version` and `app_protocol` (its own values) to `version_mismatch`, so the UI can show both sides, and `bundled` (see [Bridge start](#bridge-start)), and one message of its own:

| Message | Direction | Meaning |
|---|---|---|
| `disconnected {reason, bundled}` | app (Rust) → UI | The bridge exited or its stdout closed. `reason` is the bridge's stderr (at most 16 KiB), a protocol error, or "the hive bridge exited"; `bundled` as on `version_mismatch`. Every open terminal gets `terminal_exited {code: null}` first. Not sent after `version_mismatch`. |
| `app_mode {mode, wsl}` | app (Rust) → UI | Only where the app offers WSL or Windows (see [App mode](#app-mode-1254)), first on every `connect`: `mode` is `"wsl"`, `"native"` or null (not chosen yet: nothing starts), `wsl` whether WSL has a distribution. The UI then waits for a new connection. |

A project is `{id, name, path, worktrees, error}`: `id` and `path` are the main worktree's path, `name` its folder name, and `error` (or null) says why `git worktree list` failed, e.g. for a moved folder. A worktree is `{id, name, path, branch, main, claude, status}`: `id` is its path, `branch` is null when detached, `main` marks the main worktree and `claude` one in `<repo>/.claude/worktrees/`. `name` is the folder name for a Claude worktree and the branch otherwise (the folder name when detached). `status` is `{changes, added, removed, ahead, behind, merged, last_commit_ms}` or null (see [Worktree health](#worktree-health)). The app never derives any of these.

`AgentEvent` (internal to the service, never sent to the app) has these fields: `provider`, `terminal_id`, `session_id`, `subagent {id, agent_type}`, `cwd`, `kind`, `activity` (below), and `raw` (the unchanged payload).
`kind` is one of: `session_started`, `prompt_submitted`, `tool_started`/`tool_finished`/`tool_failed {tool}`, `permission_requested {tool}`, `notification {notification}`, `turn_finished`, `turn_failed {error}`, `subagent_started`, `subagent_stopped`, `compact_started` (`PreCompact`), `compact_finished` (`PostCompact`), `elicitation_requested` (`Elicitation`), `session_ended {reason}`, `worktree_created {name, path}`, `worktree_removed {path}`, or `other {event}`.
`notification` is one of `permission_prompt`, `elicitation_dialog`, `elicitation_url_dialog`, `elicitation_complete`, `elicitation_response`, `idle_prompt`, `agent_needs_input`, `quota_auto_resume_fired`, `quota_auto_resume_stale`, `quota_auto_resume_disabled`, or `other`.
`activity` is set on `tool_started` and `permission_requested` only: a short text from the payload's untrusted `tool_input` (`hive::adapter`): Edit/Write/MultiEdit/NotebookEdit "Editing <file>" and Read "Reading <file>", the file relative to the payload's `cwd` when inside it; Bash its `description`, else the first line of its `command`; Grep/Glob "Searching <pattern>"; Agent/Task its `description`; AskUserQuestion "Asking a question"; ExitPlanMode "Plan ready for approval"; any other tool, or a missing field, the tool's name. `compact_started` has the activity "Compacting". Control characters are dropped and it is cut at 120 characters.

### Bridge start
1. The app runs `wsl.exe [-d $HIVE_WSL_DISTRO] --exec /bin/sh -c <BRIDGE_SCRIPT> sh "$HIVE_BRIDGE" "<bundled>"` (`src-tauri/src/lib.rs`). `--exec` skips the user's login shell, so no fish config runs. On macOS (5.2) the app runs the same script natively: `/bin/sh -c <BRIDGE_SCRIPT> sh "$HIVE_BRIDGE" "<bundled>"` (`HIVE_WSL_DISTRO` is ignored). The script is a constant; both values are separate arguments, empty when absent. The script runs, in order:
   - `$HIVE_BRIDGE`, an absolute Linux path (development, `scripts/win-dev.sh`);
   - the `hive` the installer bundles (4.18): `<bundled>` is its Windows path in the app's resources, only when that file exists. a POSIX path (macOS) is used as is, else `wslpath -u` (after dropping a verbatim `\\?\` prefix) finds it in WSL; when `cmp` finds it differs from `<data>/hive/bin/hive`, it is copied to `hive.new` there, loses its `com.apple.quarantine` attribute when `xattr` exists (macOS; a missing or failing `xattr` is ignored) and is renamed over it, so a running `hive` keeps its file. On macOS the copy also gives hooks a stable path, since an app opened from Downloads runs from a random translocated one. The copy runs, so hooks (which call the daemon's `current_exe`) use it too;
   - otherwise `~/.cargo/bin/hive` (`cargo install`, development).

   `bridge_command` also tells whether the bridge runs the bundled `hive`: true when that file exists and `HIVE_BRIDGE` is empty, i.e. an installed app (12.4). `main.rs` hands it to `Hive::with_bundled`, and Rust adds it as `bundled` to `version_mismatch` and `disconnected`, so the connection dialog never tells an installed app's user to run `cargo`.

   In native mode on Windows (see [App mode](#app-mode-1254)) the app runs `hive.exe bridge` itself (`native_bridge`): the `hive.exe` bundled next to the app when that file exists (then `bundled` is true), else `$HIVE_BRIDGE` (a Windows path), else `hive.exe` on `PATH` (`cargo install`). No script: the install folder is already a stable path. The bridge then starts the service from its own copy in `%LOCALAPPDATA%\hive\bin` (12.5.5), so a running service never keeps the installer from replacing the installed `hive.exe`.

   On Windows the process gets `CREATE_NO_WINDOW`, and it is killed when the app drops the connection.
2. The bridge connects to `<runtime>/hive.sock`, only when the runtime dir is ours (owned by the user, mode 0700, not a symlink) and the socket's peer runs as the user (`peer_cred`): anything else may be another user's (9.7, `Paths::connect`, also used by `hive hook`).
3. If the connection fails, the bridge prepares the runtime dir, truncates `daemon.log` (0600) and runs `setsid --fork hive daemon`. The daemon's stdin and stdout are null and its stderr goes to the log.
4. The bridge retries the connection for up to 5 s. If the daemon never listens, the bridge fails with "the hive service did not start; see <log>".
5. Two bridges racing is harmless: the second daemon cannot take the lockfile and exits. A daemon tries the lockfile again for up to 5 s (the bridge's wait), because a service that is ending keeps it until its terminals have ended (up to their 2 s grace); that service drops its listener and removes the socket as soon as it stops serving, so a bridge started meanwhile starts the new service.
6. The bridge then copies bytes in both directions without looking at them. When either side closes, the bridge exits.

### App connect (app side)
1. The UI calls `connect(onMessage)` at startup (`connect` in `src/connect.ts`, called by `src/main.tsx`), handing a `Channel` to Rust. "Reconnect" goes through the same function, so every connection has the same handler.
2. Rust starts the bridge and queues `hello {role: app, version}`; `version` is the app's `CARGO_PKG_VERSION`, so `hive-app` and `hive` share one version number.
3. `welcome` or `version_mismatch` goes to the UI. After `version_mismatch`, Rust drops the bridge and sends nothing more.
   The UI (`src/shell/ConnectionBlock.tsx`) then blocks the workspace (`inert`, with a modal `alertdialog`; the title bar stays usable) and shows both versions and the fix: `pkill -f 'hive daemon'`, because a refused handshake leaves the old service running (the installed app brings its own `hive`), then, when `bundled`, "reinstall Hive" if it keeps happening, else (a development build) `cargo install --path crates/hive` from the same commit. `disconnected` blocks the same way and shows the reason, then "reinstall Hive" when `bundled`, else a check that `hive` is installed (`cargo install --path crates/hive`). An installed app never shows `cargo`. The dialog's "Reconnect" calls `connect` again, which starts a new bridge.
4. A UI that reloads calls `connect` again: if the connection is up, Rust closes that UI's old terminals, drops their later messages, replays `welcome` and sends `get_settings` and `list_projects` for it; otherwise it starts a new bridge.
5. When the bridge's stdout closes, Rust waits up to 2 s for its stderr, sends `terminal_exited` for every open terminal and then `disconnected {reason}`. Commands then fail with "not connected to the hive service".
6. A command that fails is shown, never swallowed (9.21): every command but `connect`, `open_terminal` and `save_file` goes through `send` (`src/transport/tauri.ts`), which shows the error text as an error toast (`showFailure` in `src/store.ts`, 10.3); its promise still rejects, already handled, so a caller that set a pending state ("Removing…", "Restarting…") ends it with `.catch`. `openTerminal` and the terminal openers built on it (`openClaude`, `openWith`, `splitTerminal`) reject; a click or key hands them to `showOpenFailure` (`src/terminals.ts`). The Biome plugin `biome/no-unshown-failures.grit` refuses `void` on any of these, and a test in `tauri.test.ts` fails on a new command sent without `send`. Toasts (10.3): the store keeps `notices` (`{ id, kind, text }`, at most 3, the newest replacing the oldest) through `showNotice`, `dismissNotice` and, in `reduce`, `withNotice`; `Toasts` shows them bottom-right above the status bar, which shows no message. An `error` stays until its × is clicked; an `info` (a confirmation: "Copied …", `pull_done`, `run_done`) fades after 4 s.

### Terminal from the UI
1. `openTerminal(cwd, cols, rows, onData)`: Rust picks the next channel (never reused while the app runs), registers `onData` and sends `open_terminal` on it. The call resolves with the channel id.
2. Output bytes for that channel go only to its `onData`. Control messages for channels the UI did not open are dropped.
3. `writeTerminal` sends terminal frames, split at `MAX_PAYLOAD`; `resizeTerminal`, `closeTerminal` and `ackTerminal` send `resize`, `close_terminal` and `ack`.
4. `terminal_exited` releases the channel's `onData`.

### Terminals in the UI (xterm.js)
`src/terminals.ts` owns every xterm.js `Terminal`, outside React (#30); output goes straight from the transport's `onData` into `term.write`, never through React state.
1. `openTerminal(cwd)` creates the `Terminal` first, then calls the transport at 80×24, so output that arrives before the tab renders is kept. It adds a tab to the store (`tabs`, `activeTab`, `selection` = the worktree path); the tab's title is the worktree's name from `projects` (the project's name is added when two tabs share a name; an unknown path shows as is).
2. `TerminalArea` renders one host element (`mountTerminals`) and calls `showTerminal(activeTab)`. Only the shown terminal is opened in the DOM, fitted (`FitAddon`) and rendered with the WebGL addon; a hidden one loses its WebGL addon and keeps parsing output into its buffer. A lost WebGL context disposes the addon (xterm falls back to its DOM renderer); WebGL is tried again the next time the terminal is shown.
3. Host size changes are debounced (50 ms) into one fit of the shown terminal; a new size sends `resizeTerminal`.
4. Keys: `interceptKeys(handler)` sees every key event first and keeps the app shortcuts from the terminal (see Shortcuts); then Ctrl+Shift+C copies the selection and Ctrl+Shift+V pastes through the clipboard API (#35; on macOS Cmd+C and Cmd+V, and Ctrl+C/Ctrl+Shift+V reach the shell); everything else goes to xterm and, as `onData`, to `writeTerminal`. Input stops once the terminal exited.
5. `closeTerminal(id)` sends `close_terminal` unless the shell already exited, disposes the `Terminal` and removes the tab (the right neighbour, or the new last tab, is shown). An exited terminal keeps its tab, marked "exited", until closed; `unhooked_agent` adds a "no hooks" badge.
6. The `terminal` settings (see [Settings](#settings)) and the theme's colors are each terminal's xterm options (`termOptions`), set on new terminals and on every open one when `settings` change (the shown one refits). With `copy_on_select`, a new selection is copied to the clipboard.
7. Each `term.write` of output has a callback: once xterm.js has parsed the bytes they count as written, and every 64 KiB (`ACK_BYTES`, under the service's 128 KiB low mark) `ackTerminal` acknowledges them (9.19, see Flow control in [Wire protocol](#wire-protocol)). Hidden terminals parse their output too, so they keep acknowledging it; an exited one stops. Output that arrives before `openTerminal` resolves is acknowledged with the next batch.

### Shortcuts (#35)
`src/shortcuts.ts` has one `keydown` listener on the window and one command table, `COMMANDS` (id, label, keys, action): `shortcut()` runs the command whose keys were pressed, and the settings' Shortcuts section lists them. A focused terminal gives each key to `interceptKeys` first: a shortcut is kept from xterm, which leaves it unhandled, so it bubbles up to the window listener and runs once; every other key (Ctrl+Shift+C/V included) is the terminal's.
1. Ctrl+Shift+T opens the worktree picker (every worktree of every project, filtered by worktree or project name; ↑/↓, Enter or a click opens a terminal in its path; Esc or a click outside closes). Ctrl+Shift+N opens the new worktree dialog for the selected project, the project of the selected worktree (a selected agent counts as its worktree, `selectedPlace` in `src/store.ts`; the tab bar's "+" uses it too), or the first project (add project when there is none). Ctrl+Shift+B toggles the files panel. Ctrl+Shift+O opens add project. Ctrl+, opens the settings. Ctrl+Shift+P opens the command palette (`src/shell/Palette.tsx`): one list, filtered by a subsequence match ranked by runs and word starts, grouped as Commands (every `COMMANDS` entry with its keys, plus `paletteCommands` extras such as "Remove merged worktrees…", "Run: <name>" for each run script of the selected worktree's project and "Send review"), Agents and worktrees (agents of every space, the current space's worktrees; Enter goes to the agent as F8 does, `goToAgent`, or selects the worktree and expands its project) and Files (the lines of the files panel's worktree holding the text, `search_files` once typing pauses; a row opens the file at that line as the Files panel does). F8 (no modifiers, or a click on the "N pending" counter) selects the pending agent after the selected one (else after the one whose terminal is shown) in tree order, wrapping; it expands the agent's project and worktree, shows its terminal when it has a tab and scrolls it into view. Agents outside every project come last. With nothing pending it does nothing.
2. On macOS every Ctrl+Shift+letter shortcut is Cmd+Shift+letter instead (and Ctrl+, is Cmd+,) (`commandKey` in `src/window.ts`, from the user agent); Ctrl+Shift+letter then goes to the terminal. Tooltips and kbd chips show `⇧⌘B` there (`keyText`).
3. Nothing runs under the connection block (`version_mismatch`, `disconnected`) or while a dialog is open; the key then goes on as usual.
4. The tree (sidebar): ↑/↓ move between rows, ←/→ collapse and expand a project or a worktree with agents, Enter selects (rows are buttons).

### Closing the app (#18)
1. The title bar Close, Alt+F4 and the taskbar all become one Tauri close request. `guardClose` (`src/window.ts`) listens to it with `onCloseRequested` and asks `confirmClose` (`src/shell/CloseAppDialog.tsx`).
2. When `agentsAtRisk` is empty, or the `agents.confirm_close` setting is off, the window is destroyed at once. Otherwise the request is cancelled and the "Close Hive?" dialog opens: Cancel/Esc keeps the app, "Close Hive" (focused, Enter) calls `closeWindow`, which destroys the window without asking again. Stage 1 counts every detected agent; Stage 2 narrows `agentsAtRisk` to working, waiting for permission and waiting for you.
3. The last window gone, Tauri emits `RunEvent::Exit`; `on_run_event` runs `Hive::shutdown`: the frame queue closes, so the bridge's stdin closes, the bridge exits and the daemon runs "App disconnect" below. Shutdown waits up to 2 s for the bridge to end, then kills it (no `wsl.exe` left behind). A crashed app closes the same pipe through the OS.
4. Outside Tauri (browser, mock transport) only the title bar Close requests a close, and a close that goes through sets `data-closed` on `<html>` for the browser checks.

### Notifications (hive.md item 5)
1. The service decides which change alerts (`states::Agent`): the `agent_state` whose displayed state changed carries `alert`: `finished` when it went from working or with subagents to waiting for you, else `waiting` when it entered waiting for permission, a plan or an answer, waiting for you or error (a pending state). An agent's first state, the snapshot after `welcome` and an interrupt (`interrupted`: the user caused it) carry none. `src/connect.ts` passes every service message to `notify` (`src/notify.ts`), which only presents the alert.
2. Each alert plays a short tone synthesized with Web Audio (no audio file) at the `notifications.volume` setting (0 plays none); changes within 500 ms share one tone.
3. `finished` is "agent finished": `showNotification` (`src/window.ts`) sends an OS notification through `tauri-plugin-notification` ("Agent finished", "project · worktree: waiting for you"), only when the message is `pending`: the service marks an agent that finished in view of the focused window as not pending (see [Agent states](#agent-states) item 5), and then there is no notification. The tone still plays. The capability allows only `is_permission_granted`, `request_permission` and `notify`. Outside Tauri nothing is shown.
4. Inbox (6.5): every alert (item 2, muted or not) is also kept in the store's `inbox` (`addToInbox`, at most 100, newest first: `{id, agent, state, at, text}`, text "<name> is waiting for permission" / "finished" / "is waiting for you" / "failed"; an optional `space` is left for 6.14). The title bar bell opens it as a menu (`ContextMenu`): the pending agents in tree order, then the alerts with relative times; an item goes to its agent through `goToAgent` (`src/shortcuts.ts`, shared with F8), an ended agent's item is disabled. A dot shows alerts newer than `inboxSeen`; opening marks them read. It lives in memory only.

### Settings
1. The service owns the settings (#37) in `<config>/hive/settings.json` (`$XDG_CONFIG_HOME/hive`, or `~/.config/hive`): `terminal {font_family, font_size 8–32, scrollback 1000–100000, cursor_style block|bar|underline, cursor_blink, copy_on_select, shell default|cmd|git_bash}` (`shell`: native Windows only, see [Native Windows terminals](#native-windows-terminals-1253); ignored elsewhere), `appearance {theme one-dark|one-light}`, `notifications {volume 0–100}`, `agents {silence_secs 2–60, confirm_close}`, `worktrees {default_base}` (null: the project's current branch), `projects {<project id>: {scripts {setup, run [{name, command}], archive}}}` (see [Project scripts and ports](#project-scripts-and-ports-68)) and `claude {accounts [{name, config_dir}], account}` (see [Claude accounts](#claude-accounts-122)). Defaults: `"Hive Mono", "Symbols Nerd Font", monospace` (a file still holding the pre-7.11 default `"IBM Plex Mono", monospace` gets it too), 13, 5000, block, no blink, no copy on select, default, one-dark, 100, 5 s, confirm, null. Every key is optional (a missing one takes its default) and unknown keys are ignored. Texts (run script names too) must be non-blank, at most 256 bytes, without control characters; scripts non-blank, at most 16 KiB, without control characters but newlines and tabs; run script names unique per project.
2. At start the service reads the file (at most 256 KiB). A missing file is the defaults. An unreadable or invalid one (bad JSON, a value out of range) is the defaults too: the app gets `settings` with them and then `settings_failed` with the reason, on every connect and `get_settings`, until settings are saved; the file is not touched until then. The warning also goes to stderr (`daemon.log`).
3. `set_settings` replaces the whole settings: checked, written (at most 256 KiB, temporary file renamed over it, mode 0600) and then in use at once (the silence rule reads it on every tick). A refusal changes nothing.
4. The store keeps the last `settings` as `settings` (`DEFAULT_SETTINGS` in `src/store.ts` until they arrive) and a `settings_failed` message as `settingsError` (cleared by the next `settings`), also shown as an error toast. The app applies the `terminal` settings to its terminals, `appearance.theme` as `data-theme` on the root element (One Light's CSS variables in `src/styles.css`, from Zed's One theme), `notifications.volume` to the tone and `agents.confirm_close` to the close guard.
5. The settings dialog (`src/shell/SettingsDialog.tsx`, Ctrl+,) shows them by section (Terminal, Appearance, Notifications, Agents, Accounts, Worktrees, Projects, Shortcuts, About), or every field whose label matches the search. The Terminal section's Shell select shows only while the app runs the service natively on Windows (`appMode.mode` `native`, 12.5.4). A change sends `set_settings` with the whole settings (text and number fields once typing pauses for 400 ms), one at a time: a change made while one waits for its answer (`settingsPending`) is sent once it arrives, built on it, so a quick second change cannot undo the first. Run script rows carry a key of their own, so a rename keeps the focus and a late edit finds its row. `settingsError` shows at the top. "Open settings file" sends `open_settings_file`. About shows the app's version (`package.json`), the service's (`welcome`), `diagnostics` (asked when the section opens) and the terminals with an `unhooked_agent` badge.

### Projects
1. After `welcome` (also a replayed one), the app's Rust side sends `list_projects`; the UI's "Refresh worktrees" button sends it again. The service also sends `projects` after each worktree hook (see [Worktree hooks](#worktree-hooks)); any other change of git's worktree registry reaches the app through `hive::registry` (9.36).
2. The service answers `projects`. Each project's worktrees come from `git worktree list --porcelain -z`, bare and prunable entries (the directory is gone) skipped. Git gets 10 s (killed with its children after it, as for [Worktree health](#worktree-health)); a timeout is that project's `error` only (9.13).
3. `add_project {path}` (the add-project dialog): the path must be absolute, an existing directory and inside a git repository with a working tree. It is normalised to the main worktree (the first entry of `git worktree list`), so a subfolder or a linked worktree adds its repository. A new project is appended to the current space in `<data>/hive/spaces.json`; if that write fails the list is unchanged and the answer is `add_project_failed {error: storage}`. A project already in another space is refused (`in_other_space`, "<path> is already in the space <name>").
4. Project requests run on a blocking thread, off the app's frame loop, because git can be slow.
5. Worktree requests name a project by id and are refused ("<id> is not a followed project") for any other.

### New worktree (screens 1c/1d)
1. The dialog opens for a project (the row's "New worktree", or `openModal("new-worktree", id)`), sends `list_branches` and `validate_worktree_name` for the empty name.
2. Every keystroke in the name sends `validate_worktree_name`: the service runs `worktree::check_name` (the rule and the existing-folder check of `hive worktree create`, no git), so the dialog never has its own rule (#33, #37). Create stays disabled until the current name has a clean verdict.
3. The branch list is filtered in the UI (case-insensitive substring) and virtualized (TanStack Virtual); ↑/↓ in the filter move the pick. A pick hidden by the filter gives way to the first branch shown.
4. `create_worktree` runs `worktree::create`, the CLI's code. On `worktree_created` the UI selects the new worktree, runs the project's setup script, if any, in a terminal tab of its own (`openWith`), opens a terminal tab in it if asked (`openTerminal` of `src/terminals.ts` with its path), and closes the dialog; with notes, the dialog stays open to show them.

The list is `spaces.json`, `{current, spaces: [{id, name, projects, env}]}`, written through a temporary file (mode 0600) renamed over it. Without it, the flat list of earlier versions (`projects.json`, a JSON array of paths) becomes the "Default" space (id `default`), and is left as it is; `spaces.json` is written on the first change. A missing file is an empty list. An unreadable or invalid one (bad JSON, over 1 MiB, or breaking a space rule: no space, an unknown current one, a repeated id, a project in two spaces, a bad name or environment) is moved to `<name>.corrupt` with a warning on stderr (`daemon.log`), and the service starts with an empty list.

### Spaces (6.14)
A space groups projects (work, personal) with an optional identity for the terminals opened in them. Agents of every space stay alive and keep alerting.
1. Rules (`hive::spaces`): a name is trimmed, not blank, at most 64 characters, without control characters. Each `env` value is trimmed and blank means unset; git name and email are at most 256 bytes, the two folders at most 4096 bytes and absolute, all without control characters. A `gh_account` login is 1–39 ASCII letters, digits, `-` or `_`, its host 1–253 letters, digits, `.`, `-` or `:`, neither starting with `-`. On `create_space`/`update_space` the folders must exist as directories (a file read at start only needs the shape, so a folder gone later does not lose the list). New spaces get the ids `space-<n>`, the first free `n`. A project is in one space only. Only a space without projects is deleted, never the last one; deleting the current one makes the first one current. Every change is saved at once; a refused or unsaved one changes nothing (`space_failed`).
2. A terminal opened in a worktree of a project gets its space's `env` as environment entries (never a shell string): `GIT_AUTHOR_NAME` + `GIT_COMMITTER_NAME`, `GIT_AUTHOR_EMAIL` + `GIT_COMMITTER_EMAIL`, `GH_CONFIG_DIR`, only those set, and with a `gh_account` its token plus `GH_HOST` (item 6). The placement uses `projects::place` on the terminal's `cwd`; outside every project nothing is added. Changes apply to terminals opened afterwards.
3. The Claude account is not the space's (12.2, [Claude accounts](#claude-accounts-122)): the terminal keeps the Claude config folder it was opened with, and an agent detected in it takes it: its session name is read from `<folder>/projects`, else from the service's own root (`$CLAUDE_CONFIG_DIR/projects`, else `~/.claude/projects`), and its transcript is read when it lies inside that folder or any account's. The Sessions panel (`list_sessions`, `locate_session`, `delete_session`) covers the current space's projects in every account's folder.
4. UI: a select at the left of the sidebar header lists the spaces plus "New space…" and "Edit space…" (the dialog `SpaceDialog`: name, git name, git email, GitHub CLI config folder; "Delete space" only enabled for an empty one). The sidebar shows the current space's projects (`spaceProjects`); the Sessions panel lists again when the space changes. The pending bell, F8, tones and OS notifications cover every space; a notification and each inbox item (pending or kept) name the agent's space when there are several (`agentPlace`, `spaceName` in `src/notify.ts`; `InboxItem.space`), and going to an agent of another space (`goToAgent` in `src/shortcuts.ts`, used by F8 and the inbox) sends `select_space` for it.
5. Removing a project (9.28): "Remove project…" in the project row's menu and in the palette asks through `ConfirmDialog` (`askRemoveProject`: names the project, says its files stay on disk, and warns when one of its file tabs has unsaved edits), then sends `remove_project`. The service refuses it while a process of one of its own terminals (by the terminals' session ids in `/proc`) works in the project or one of its worktrees, then takes it out of its space (`Spaces::remove`, saved as every space change) and drops its settings and port blocks (best effort, after the spaces are saved). Its space may then be deleted if it became empty. Adding the folder again later is a fresh add. The app's `project_removed` drops its rows and sessions, its file tabs, the panel state of its worktrees (files, changes, comments, new folders, search, collapsed folders) and its keys in `hive.agentOrder` and `hive.tabOrder`; `remove_project_failed` shows as an error toast.
6. GitHub account (9.30): a space may name one of the accounts logged in to `gh` (the human has several and switches with `gh auth switch` by hand); Hive uses it without changing `gh`'s active account. `list_gh_accounts` runs `gh auth status` (in the dialog's `GH_CONFIG_DIR`, checked as the space's folder is): `gh` checks each token with GitHub, so it runs only when the dialog opens or its config folder field is left, never polled. Its lines "✓ Logged in to <host> account <login> (<source>)" / "X Failed to log in to …" and "- Active account: true|false" give the list (at most 32; bad logins or hosts left out); exit 1 with none is "not logged in". When a terminal of the space opens, `gh auth token --hostname <host> --user <login>` (in the space's `GH_CONFIG_DIR`) gives the token, trimmed and kept only when it is 1–1024 printable ASCII characters; it goes into that terminal's environment only (`GH_TOKEN` on github.com and `*.ghe.com`, `GH_ENTERPRISE_TOKEN` on other hosts, where `gh` ignores `GH_TOKEN`), never to the app, a log or a file. No token (no `gh`, logged out): the terminal opens without it, and the reason (naming the login, never a token) goes to `daemon.log` and to the app as `notice`, so the human knows it acts as `gh`'s active account. `gh_accounts` carries logins only. "Make active in gh…" (shown when the chosen account is listed and not active) asks through `ConfirmDialog` (its `back` keeps the space dialog open underneath) before `switch_gh_account`. For 9.31/9.32, `Gh::run(env, cwd, args, limit)` runs `gh` for a project as its space's terminals would (`Projects::space_env(cwd)` gives the space's environment; `State::gh()` gives `gh` on the user's `PATH`); its error is `gh`'s stderr (never its stdout), fit to show as is. Recordings of the real output (gh 2.46): `scripts/spike/record-gh.sh`.

### Claude accounts (12.2)
Several Claude accounts at once, independent of the space: an account is a name and a `CLAUDE_CONFIG_DIR`.
1. The service keeps them in the settings (`claude.accounts`, `claude.account`, `hive::settings`). The default account (no `CLAUDE_CONFIG_DIR`: `~/.claude`, or the service's own) always exists, is not in the list, cannot be renamed or removed, and is named "Default". A name is checked as a space's (trimmed, not blank, at most 64 characters, no control characters), unique and not "Default"; a folder as a space's were (absolute, at most 4096 bytes, printable) and unique; neither with spaces around it. A folder must exist when `set_settings` adds it (one already there may be gone since). `claude.account` is the current account's folder; one no account has (removed, or a hand edit) is the default account.
2. A new terminal gets the current account's folder as `CLAUDE_CONFIG_DIR` (none for the default), or the account `open_terminal` asks for. Open terminals keep theirs; so does the agent detected in one (see [Spaces](#spaces-614) item 3, and `restore_sessions`).
3. The Sessions panel lists the sessions of every account (the default one's projects folder, then each account's), whichever is current; each carries its account's folder (`config_dir`). Resuming or forking one opens its terminal with that account (`resume` in `src/sessions.ts`), and "Copy Resume Command" prefixes `CLAUDE_CONFIG_DIR='<folder>'` for another account's. Claude's records of running `claude`s are read beside each projects folder (`<folder>/sessions/<pid>.json`).
4. Migration: spaces used to hold `claude_config_dir` in their `env`. At start, each distinct one in `spaces.json` becomes an account named after its space ("Work", then "Work 2"… when taken), unless an account has that folder; the settings are saved first, then `spaces.json` without the field. A failure (an ignored settings file, which is never replaced; a write that fails) leaves both files as they were and is retried at the next start, so nothing is lost. The current account is not changed.
5. UI: the status bar's `AccountSelect` (hidden while there is only the default account; the current account's session usage, 12.1, follows it) shows the current account and saves `claude.account` through the settings' `saveSettings`. ### Pull requests (9.31)

The right panel's "PRs" view shows the pull requests of the shown worktree's project; 9.32's "Actions" view goes beside it and reuses its pieces (`hive::gh::Gh::run`, the `run` helper and `Cache` pattern of `hive::pulls`, the view's refresh).

1. ### Worktree health
1. `hive::health` reads, per worktree, on a blocking thread and with a 10 s limit per git command (git and its children, in their own process group, are killed after it): `changes` = the entries of `git status --porcelain=v2 -z --untracked-files=all --find-renames` (as `changes` counts them, so linked worktrees inside the main one count as untracked folders unless ignored); `added`/`removed` = their lines against `HEAD` as the Changes panel totals them against `HEAD` (`changes::totals`: `git diff --numstat -z --find-renames --no-ext-diff --no-textconv HEAD --`, plus every line of an untracked text file within the Changes panel's limits, 8 MiB a file and 32 MiB a listing; a binary file adds none; a `git diff` that fails or times out gives 0 lines and keeps the rest of the status; optional in the protocol, 0 from an older service); `last_commit_ms` from `git log -1 --format=%ct HEAD`; for a linked worktree, when the main worktree is on a branch, `ahead`/`behind` from `git rev-list --left-right --count HEAD...refs/heads/<branch> --`, and `merged` = `ahead` is 0 (every commit of its `HEAD` is on that branch, what `git merge-base --is-ancestor` answers, without another git run). The main worktree has `ahead`/`behind` null and `merged` false. Any git failure (no commit yet, the branch is gone, the time limit) makes the status null; `projects` never fails because of it.
2. Every message carrying projects (`projects`, `project_added`, `worktree_created`, `worktree_removed`, `worktree_renamed`) carries fresh statuses. The service remembers the last status sent per worktree path (`health::Sent`) and sends `worktree_status` only when one differs: every 30 s for every followed worktree (first right when the service starts), and for the watched worktree after each of its changes (after its `changes`, whose `git` runs it reuses when they were listed against `HEAD`).
3. The sidebar shows the status as muted badges after the worktree's row: `↑ahead`, `↓behind` (each only when not 0), the lines as `+added −removed` in the added/removed colours (`Counts`, as a changed file shows them: a side that is 0 shows nothing; the tooltip "3 changed files, +12 −4 lines"), or `●changes` ("2 changed files") when the changes add no lines (binary or empty files) and "merged", each with a tooltip. The project row's context menu has "Remove merged worktrees…" (`RemoveMergedDialog` in `src/shell/WorktreeMenu.tsx`): it lists the project's linked worktrees that are merged with no changes, as they were when it opened, all checked, and sends a plain `remove_worktree` (never `force`) for each checked one; each shows "Removing…", "Removed" or its `remove_worktree_failed` message (kept by path in `worktreeDialog.removeFailures`). Nothing is ever merged (#12).

### Project scripts and ports (6.8)
1. A project's scripts live only in the settings (`projects.<id>.scripts`), edited in the settings dialog's Projects section (a project Select; setup and archive text areas; run scripts as name + command rows with an Add form); they are never read from a repository, so a cloned repository cannot run code on its own.
2. Setup: after `worktree_created`, the new worktree dialog opens a terminal in the worktree and types the setup script + Enter into it (`openWith` in `src/terminals.ts`, the mechanism "Start claude" uses), before the dialog's own terminal. Run: the worktree's context menu has "Run: <name>" per run script of its project; each opens a terminal there and types the command + Enter. From then on Hive only observes.
3. Ports: the first time a process needs them, a worktree gets a block of 10 ports, the lowest free one of 20000–29999 (below Linux's ephemeral range), kept by worktree path in `<data>/hive/ports.json` (0600, temporary file + rename) so it stays the same across restarts. Blocks of worktrees whose folder is gone are taken back when a new block is given. A file that cannot be read, or a block outside the range, counts as none.
4. Every terminal whose `cwd` lies in a followed worktree gets `HIVE_PORT` (the first port of its block; left out when no block can be saved, with a warning on stderr), `HIVE_WORKTREE_PATH` and `HIVE_ROOT_PATH` (the project's main worktree), as environment entries.
5. Archive: `remove_worktree` first checks the worktree (linked, of a followed project; unless `force`, not in use), then the service runs the project's archive script, if any, as `sh -c <script>` in the worktree with the `HIVE_*` entries, stdin from `/dev/null`, stdout and stderr together, in its own process group (on native Windows: see [Native Windows processes](#native-windows-processes-1256a)). After 60 s the group is killed. A failure (exit code not 0, a signal, the time limit) cancels the removal with `remove_worktree_failed` whose message ends with the last 4 KiB of the output ("the archive script failed (exit status: 4):\n…"); with `force` the removal goes on anyway. Once the script ends, whatever it left in its process group is killed (its worktree is about to go); the removal waits at most 0.5 s more for output held by a process that left the group.

### Files panel watch (3.1, #31)
1. `followPanel` (`src/follow.ts`) keeps the service watching `panelWorktree`: while the files panel is open, the selected worktree (a selected project is its main worktree, which has the same id) or the selected agent's worktree. It sends `watch_worktree` when that changes, `unwatch_worktree` when the panel closes, and `watch_worktree` again after a new `welcome` (a new service has no watch). The store keeps the last `files` as `worktreeFiles` (`{path, files, truncated}`). The panel's "All" mode shows it when `path` matches, each file with its status from `changes` and the changed files it no longer lists (deleted ones) merged in (`allFiles` in `src/shell/RightPanel.tsx`, presentation only); a truncated list says so. "Changed", or "All" before the list arrives, shows only `changes`.
2. The service checks the path against the followed projects' worktrees, stops the previous watch task, and starts one (`hive::files::Watcher`, git on a blocking thread). The worktree's git dir comes from `git rev-parse --absolute-git-dir` (a linked worktree's is under the main repository's `.git/worktrees/<name>`).
3. Listing: `git ls-files --cached --others --exclude-standard -z` (at most 32 MiB read; names that are not UTF-8 and nested repositories `dir/` skipped; duplicates from conflicts merged; sorted; capped). Every git command Hive runs has `GIT_OPTIONAL_LOCKS=0`, so reading never rewrites the index the watcher sees.
4. Watches (the `notify` crate: inotify on Linux, FSEvents on macOS; each directory non-recursive): the directory of every listed file, every untracked directory (`git ls-files --others --directory`, so a new empty folder is watched), at most 8192; never inside ignored trees such as `node_modules` or `target`. In the git dir only `HEAD` and `index` count. Each re-list removes the watches of directories no longer listed before adding new ones (a renamed directory keeps its inotify watch, which must not be reused).
5. Any other event, a queue overflow included, starts a burst; 200 ms after its last event (at most 1 s after its first) the worktree is listed again from scratch. `State::worktree_changed` (`hive::daemon`) is the single point that reports the change: it sends `files` when the list differs from the last one sent, then the worktree's `changes` every time (an edit changes the diff, not the list).
6. Known limit: in a chain of new empty untracked directories (`mkdir -p a/b/c`) only the top one is watched until a file appears; a file created deep inside it later shows up on the next re-list.

### Changes
The files panel (screen 1g, "Árvore de arquivos com diff do git").
1. The panel shows the selected worktree (a selected project is its main worktree), the selected agent's worktree, or else the shown terminal's (`panelWorktree` in `src/store.ts`). When it opens and whenever that worktree or its base changes it sends `list_changes {path, base}`; the answer is stored by path in `changes`.
1. Base (9.11): a toggle in the summary line, HEAD | `<branch>`, picks what the worktree is compared with: `HEAD` (what is not committed yet) or `branch`, the merge-base of its `HEAD` and the main worktree's branch (the branch 6.6 counts ahead/behind against, `health::branch`), so an agent's commits stay in view. The pick is UI state (`diffBases` by worktree path, this run only, not remembered); the default is `branch` in a Claude worktree and `HEAD` anywhere else (`diffBase` in `src/store.ts`). The toggle shows when the answer has a `branch` or a `base_error`; with a `base_error` the list is against `HEAD` and the branch button is disabled, its tooltip saying why. The main worktree has no toggle. `followPanel` sends `watch_worktree` again when the base changes, and `followOpenFile` asks for the open file again.
2. The service refuses a path that is not a worktree of a followed project, then runs, on a blocking thread: `git status --porcelain=v2 -z --untracked-files=all --find-renames` and `git diff --numstat -z --find-renames --no-ext-diff --no-textconv <base> --`. Against `HEAD` the base is `HEAD`, or the empty tree (`git hash-object -t tree /dev/null`) before the first commit, so staged, unstaged and untracked changes all count, as `git status` shows them. For `branch` it is `git merge-base HEAD refs/heads/<main branch>` (exit 1, no output: no common commit), and the files are `git diff --raw -z --find-renames <merge-base> --` (committed since it, staged or not: `A` added, `D` deleted, `R` renamed with its source, anything else modified) plus the untracked entries of `git status`: one git run more than against `HEAD`, since the merge-base replaces `rev-parse HEAD`. Without a main branch (the main worktree itself, or a detached one), without a common commit or when `merge-base` fails, it lists against `HEAD` and says why in `base_error`. A detached `HEAD` in the worktree still has a merge-base. The refresh of the watched worktree lists the projects once for both its `changes` and its status, and its status's `changes` count is the entries of the `git status` just run (9.14), not a second one.
3. Status per file against `HEAD`: `?` untracked; `2` (rename) renamed with its source; `1` added when the index says `A`, deleted when either side says `D`, else modified; `u` (unmerged) modified; ignored entries skipped. Line counts come from numstat (`-` = binary = null). An untracked file is counted here: a regular file of at most 8 MiB with no NUL in its first 8000 bytes (git's binary test) has as many lines as newlines, plus one for an unterminated last line; anything else is null. One listing reads at most 32 MiB of untracked files (9.14, default pending the human's review): once a file does not fit in what is left, it and every file after it are null.
4. Limits: each git command's output is read up to 16 MiB (more is an error, and git stops on the broken pipe); file names are kept as bytes to read the file and sent as lossy UTF-8. The files go into the message until their JSON reaches 3 MiB, well under `MAX_PAYLOAD`; the rest are left out with `error` "too many changes: N files not shown", while the totals still count every file.
5. The UI groups the paths into folders (presentation), folders first; a folder shows the strongest status inside (deleted > added > renamed > modified), and a collapsed one a dot of that color (`collapsed["folder:<worktree>/<path>"]`). Letters: M, A (added and untracked), D (struck through), R. The tree is virtualized and is one focusable element: ↑/↓ move, ←/→ collapse and expand, Enter opens a file or toggles a folder. Opening a file sets `openFile {worktree, path}`; `FileView` (in `src/shell/RightPanel.tsx`) shows its header under the tree and, below it, the file (see [Viewer and diff](#viewer-and-diff-33-31)). "All" / "Changed" is `changedOnly`; until the full file list exists (3.1) both show the changed files.

### Viewer and diff (3.3, #31)
1. `followOpenFile` (`src/follow.ts`) sends `open_file {worktree, path, base}` when `openFile` is set, again whenever a new `changes` for its worktree arrives (the file may have changed with it) or its base changes, and after a new `welcome`. The store keeps the last answer as `file`; `FileView` shows it only while it is the open file.
2. The service checks the worktree against the followed projects and the path on a blocking thread: not empty, at most 4096 bytes, only normal components (no `/` start, `.` or `..`); on disk it is resolved (`canonicalize`, symlinks followed) and must stay inside the worktree's resolved path and be a regular file (never a FIFO or device, which could block). A missing file has no `content`.
3. `base`: the base is resolved as for `list_changes` (the merge-base, or `HEAD`). At `HEAD`: nothing before the first commit (`git rev-parse --verify --quiet HEAD`); else the blob of `git --literal-pathspecs ls-tree -l -z <base> -- <path>` (a tree or submodule entry counts as none); a path absent there that is a rename takes its old path's blob: against `HEAD` a staged rename (`git status --porcelain=v2 -z --untracked-files=no --find-renames`), against the merge-base a rename since it (`git diff --raw`, as the list). The blob is read with `git cat-file blob <id>`.
4. Limits: each side is read up to 1 MiB (`TEXT_LIMIT`; the blob size from `ls-tree` is checked first); over it, `too_large`. A side with a NUL in its first 8000 bytes (the rule of [Changes](#changes)) or that is not UTF-8 makes the file `binary`. Both leave both texts null. If the JSON of the answer would still exceed `MAX_PAYLOAD` (escaping can double text), it is sent as `too_large` without texts. Both sides missing is the error "<path> does not exist".
5. `version` = `<byte length>-<64-bit SipHash of the bytes, hex>` (`hive::file::version`, Rust's `DefaultHasher`, stable within one build of the service). A save recomputes it from the file on disk and compares for equality (see [Editing](#editing-35-31)).
6. UI (`src/viewer/`): `CodeView` creates one CodeMirror `EditorView` per open file (keyed by worktree and path), outside React state (#30), through `createViewer` (`editor.ts`), and calls `show({content, original})` with each answer: a new read-only state that keeps the scroll position. A file among the worktree's `changes` shows as `unifiedMergeView` (`@codemirror/merge`, no merge controls, unchanged stretches over 6 lines collapsed to a margin of 3) with `original` = `base` (a deleted file: empty content, all removed; a new one: empty original, all added); any other file shows its text under "No changes in this file.". `binary`, `too_large` and `error` show a message instead ("Binary file not shown.", "File too large to show.", the error). The language comes from the file name through `@codemirror/language-data`, loaded on demand; the look is One Dark with the prototype's surfaces and diff colors.

1. Which views are editable: a file without changes opens (from the tree) as editable text; a changed file opens as its read-only diff (#31: the diff stays read-only) and the header's "Edit" switches it to editable text, "Diff" back (disabled while there are unsaved edits). No LSP.
2. The buffer (`src/viewer/buffer.ts`, pure; kept in the store as `edit`, so it survives the panel closing) holds the text being edited, the text on disk it is based on and its `version`. The CodeMirror view (`createEditor` in `editor.ts`) is created once per open file outside React state (#30); it splits lines on "\n" only, so a "\r" is text and saves unchanged. Undo, the standard keys and Tab indenting come from `@codemirror/commands` (Esc, then Tab, leaves the editor).
3. Save: Ctrl+S while the editor has the focus (a CodeMirror key, so the terminal never loses it and no app-wide shortcut is taken, #35) or the header's Save sends `save_file` with the buffer's base `version`; one save at a time. A save the app cannot send (not connected, over the frame limit) fails at once with the reason. `file_saved` makes the sent text the new base; the header's dot marks unsaved edits.

### Daemon start
1. Prepare the runtime dir (0700, owned by the user).
2. Take the lockfile with an exclusive `flock`. If it is already held, exit with an error.
3. Install the wrapper and the hooks settings.
4. Remove any stale socket, bind it and set it to 0600.
5. Serve.

### Native Windows service (12.5.2)
The same daemon, bridge, hook and badge, over a named pipe instead of the socket (`hive::windows`):

- **Paths.** Data in `%LOCALAPPDATA%\hive` (else `%USERPROFILE%\AppData\Local`, else the temporary folder), the lock and `daemon.log` in its `run` folder (created with the folder's inherited ACL: the user's local app data), settings in `%APPDATA%\hive`.
- **Pipe name.** `\\.\pipe\hive-<SID>-<hash>`: the SID (`S-1-5-21-…`) of the user the process runs as (its token's `TokenUser`), and the FNV-1a hash (16 hex digits) of the runtime folder's path. The hash plays the part of `XDG_RUNTIME_DIR` on Unix: one service per user and data folder, so a test's service (temporary `LOCALAPPDATA`) never meets the real one.
- **Server.** The first instance is created with `first_pipe_instance(true)`, so a pipe of that name already there (another service, or someone squatting the name) makes the daemon exit with the error; `reject_remote_clients(true)`; a security descriptor `O:<SID>D:P(A;;GA;;;<SID>)`: the user as owner (an elevated process would otherwise make the administrators the owner), a protected DACL with all access for the user only. Each connected instance is handed to the connection task and a new one waits for the next client; the lock (`hive.lock`, `File::try_lock`, retried for 5 s) still keeps one service per data folder.
- **Client** (`Paths::connect`, used by the bridge, `hive hook`, `hive badge`, `hive worktree hook-*`): opens the pipe, retrying every 10 ms while every instance is busy (`ERROR_PIPE_BUSY`), for at most 2 s; then the pipe's owner (`GetSecurityInfo`) must be the same SID, else "refusing a hive pipe of another user (<SID>)". This replaces the socket's `check_peer`. It checks the pipe object, not the serving process (`GetNamedPipeServerProcessId`, the plan's first idea): a pipe instance handed to another process keeps its creator's process id, which one of the user's own processes could later reuse, while another user cannot make an object the user's without a privilege (security review).
- **Known gap** (as 9.7 on macOS): the name is predictable, so another local user can create it first (with the owner check, only to keep the service from starting, never to reach its clients). An unguessable name kept in a file of the runtime folder would close it.
- **Daemon life.** The bridge starts `hive daemon` with `DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP | CREATE_BREAKAWAY_FROM_JOB`, again without the breakaway when its job forbids it (cargo's does), stderr to `daemon.log`. Nothing signals a detached daemon: it ends when the app connection ends (the bridge exits when the app closes its stdin, or when the app kills it).
- **Clock.** `sent_ns` is the performance counter (`QueryPerformanceCounter` / `QueryPerformanceFrequency`, in ns), one clock for every process on the machine like `CLOCK_MONOTONIC`.
- **Files** (12.5.6b). A folder moves with `MoveFileExW` without `MOVEFILE_REPLACE_EXISTING` (an existing target fails, as `renameat2(RENAME_NOREPLACE)`); a file save still renames a temporary file over the file, and when another program keeps the file open without sharing it (a sharing or lock violation on the version check's open, access denied on the rename; also what a file Hive may not write gets) it answers `save_failed` `io` "<name> is open in another program, or cannot be replaced: close it there and save again (…)", the file untouched and the temporary file removed. The editor target, the settings file and a session's log or folder are the paths themselves (no `wslpath`); nothing is refused for its permission bits (Windows has none). Resolved paths lose `\\?\` (`\\?\UNC\` becomes `\\`) before git gets them or they are compared; the paths git prints (worktrees) use `\`, while the relative paths the file operations answer keep `/`, as git lists them. Counting an untracked file's lines opens it plainly (no FIFO on Windows). The folder browser: see `hive::dirs`. The watcher (`notify`, `ReadDirectoryChangesW`) watches the same folders as on Linux; Windows also reports a folder as modified for a write anywhere under it (an ignored tree too), so a folder's own change (a modify event on a folder, also a mode change on Unix) counts for nothing: what it holds has its own watch or is ignored.
- **Hooks, the `claude` wrapper and the statusline:** see [Claude Code on native Windows (12.5.5)](#claude-code-on-native-windows-1255).
- **Tested** by `windows.yml`: `hive::windows`'s unit tests (the pipe, busy and missing service, the SID, the clock, the detached start) and the integration test `tests/integration/windows.rs` (the bridge starts the service, the app's handshake, terminals (see below), a hook-role connection's report reaches the app, `hive hook` exits 0 quietly, and the service ends once the app leaves).

### Native Windows terminals (12.5.3)
The same `open_terminal`, input, `resize`, `ack` flow control and `close_terminal` as on Unix ([Terminal open and close](#terminal-open-and-close)), on a pseudoconsole (`hive::windows::terminal`; the portable parts, tested on every OS, are `terminal::conpty`):

- **Shell** (`terminal.shell` in the settings, read when a terminal opens): `default` is `pwsh.exe` when it is on the service's `PATH`, else `powershell.exe`, started with `-NoExit -Command <FOLLOW>` (`conpty::FOLLOW`: once the profile ran, its prompt, the user's wrapped, first sets the process's working folder to its file-system location, which `cd` alone never moves; see [Native Windows processes](#native-windows-processes-1256a)); `cmd` is `cmd.exe`; `git_bash` is `<Git>\bin\bash.exe --rcfile <data>/shell/bashrc -i` (12.5.5; the rc path in Git Bash's form, `/c/…`), `<Git>` being two folders above the first `git.exe` on `PATH` that has one (`<Git>\cmd\git.exe`), else the terminal does not open ("Git Bash was not found: no git.exe on PATH"). The rc file is macOS's bash one (`terminal::login`): it runs `/etc/profile` and the first of `~/.bash_profile`, `~/.bash_login`, `~/.profile`, as a login bash does, then puts `$HIVE_BIN_DIR` first on `PATH` and unsets it; a login bash (`--login`, 12.5.3) put Git's own folders, and whatever the user's profile adds, before Hive's bin folder. An unknown value makes the settings file invalid (serde), so it is checked in Rust.
- **Start.** Two named pipes `\\.\pipe\hive-console-<pid>-<n>` (created as the service's pipe is, only this user can open them): the console host writes the output to one and reads the typing from the other. `CreatePseudoConsole` of the terminal's size, then `CreateProcessW` with the pseudoconsole attribute, `CREATE_SUSPENDED` and invalid standard handles (the service's own are its log), in the terminal's `cwd`. The shell joins a new job with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` (so nothing it started outlives the service), then resumes. Its process id is the terminal's session id.
- **Environment:** the service's, then `HIVE_TERMINAL_ID`, `TERM=xterm-256color` and the terminal's own (`CLAUDE_CONFIG_DIR` of its account, its space's, its worktree's `HIVE_*`), names compared ignoring case, then Hive's bin folder first on `PATH`, and `HIVE_BIN_DIR` (that folder in Git Bash's form, for its rc file).
- **Resize:** `ResizePseudoConsole`, only while the console is open.
- **End.** The shell's exit is watched by a thread waiting on its process handle. Ending a terminal (its tab closed, its shell exited, the app gone) closes its pseudoconsole (`ClosePseudoConsole`, on a thread of its own: it waits for the console host, which may wait for its output to be read), which sends its programs `CTRL_CLOSE_EVENT` as SIGHUP does; after at most 2 s with processes still in the job, `TerminateJobObject` kills them with exit code 9. A shell that exits leaves the console open (its output never ends by itself), so the pump's 200 ms drain always runs before it closes.
- **Unhooked `claude`:** a process is in a terminal's session when it is in that terminal's job (`JobObjectBasicProcessIdList`, at most 1024 per terminal); see [Native Windows processes](#native-windows-processes-1256a).

### Native Windows processes (12.5.6a)
What the service runs and watches outside its terminals (`hive::windows`):

- **Process table** (`windows::list`, `sysinfo`, a Windows-only dependency): every process, named by its file without `.exe` (`claude.exe` is `claude`), with its process id as its `pgrp` and, when it is in a terminal's job, that terminal's session (else 0). A terminal's processes also get their command line read (one read of the process's memory each, so only theirs): a `node` running `…\@anthropic-ai\claude-code\cli.js` is npm's `claude` and counts as `claude` (`terminal::conpty::comm`). A process's arguments and open files are not read (`procs::claude_sessions` then knows a `claude`'s session only from Claude's own record).
- **Working folders** (`windows::inside`, for the worktree busy and held checks of `projects`, `file` and `daemon::app`): every process's working folder is read at once (a process's own, from its memory); it and the folder are resolved (`paths::canonical`: 8.3 short names, junctions, links and `subst` drives, no `\\?\`; as they are when that fails), and one is inside the folder when its names start with the folder's, compared ignoring ASCII case. Command Prompt's `cd` moves its working folder and PowerShell's follows its location at each prompt (`conpty::FOLLOW`), but the msys `cd` of Git Bash moves neither its own nor its launcher's: a Git Bash terminal counts where it started, and a program it starts where that program runs. So, as on Unix, a worktree some process works in is not removed, renamed or moved without `force`: Windows would refuse to delete a process's working folder only after `git worktree remove` had deleted the files in it. A process Windows does not let the user read (another user's, a protected one) has no folder.
- **Time limits** (git, `gh`, project scripts): the program joins a new job (`windows::Job`, `KILL_ON_JOB_CLOSE`, as a terminal's) right after it starts, so everything it starts is in it too; the limit ends the whole job with `TerminateJobObject` (exit code 9), as the process group is killed on Unix, and so does the end of an archive script. A program that cannot join a job is killed (it would run without a limit). Dropping the job, once the program was waited for, also ends what it left running. (Not started suspended in it as a terminal's shell is: `std::process::Command` cannot resume a process; a program starts nothing in the microseconds before it joins.)
- **Archive scripts** run in the terminals' shell (`terminal.shell`, found as for a terminal): PowerShell `-NoProfile -Command <script>`, Command Prompt `/D /S /C "<script>"` (the line as it is: `cmd` has quoting rules of its own; `/D` skips its AutoRun; a script of more than one line is refused, which cancels the removal: `cmd` would run its first line only), Git Bash `-c <script>`; Git Bash missing fails the script ("Git Bash was not found: no git.exe on PATH"). Same 60 s limit, environment and output as on Unix; a failed script's message says `exit code: N`, Rust's wording on Windows.
- **`gh`** is looked for as `gh.exe` only in the absolute folders of the user's `PATH` (`windows::on_path`): given a bare name, Windows would also find it beside Hive, in its system folders and on the service's own `PATH`.

### App mode (12.5.4)
On Windows the service runs in WSL or on Windows itself, one at a time (human answers 2026-09-28). The app's Rust side keeps the choice, since it is needed before any service starts (`hive_lib::Modes`, `src-tauri/src/lib.rs`):

- **Gate.** Offered only when `HIVE_MODE=native` is set, until 12.5.7; otherwise (and always on macOS) the app runs the WSL bridge as before, sends no `app_mode`, and the UI shows no choice.
- **WSL.** `wsl.exe -l -q` (`CREATE_NO_WINDOW`) run once at start, unless Windows is saved (WSL was there when it was chosen), and killed after 3 s (no answer counts as no WSL): WSL has a distribution when it succeeds and prints a letter or digit (it prints UTF-16, or UTF-8 with `WSL_UTF8=1`; a missing WSL or distribution fails or prints nothing). Without one the service runs on Windows, never asking, and the settings offer no switch.
- **Store.** The file `mode` in the app's config folder (`%APPDATA%\com.lucas.hive\mode`): `wsl` or `native`. None (or anything else) with WSL present: the first run, which asks.
- **Connect.** `connect` sends `app_mode` first. With no mode yet it starts nothing: the UI blocks the workspace with "Where should Hive run?" (`ModeChoice` in `src/shell/ConnectionBlock.tsx`; WSL or Windows). Otherwise it starts that mode's bridge (see [Bridge start](#bridge-start)).
- **Choose.** The command `set_mode {mode}` saves the file (a failure is an error toast, nothing changes), then, in the background, ends the connection as the app's exit does (`shutdown`: every terminal exits, `disconnected`) and connects the same UI again (`app_mode`, then the new service's `welcome`, `settings`, `spaces`, `projects`). The first-run dialog and the settings' "Service" select (Terminal section, shown only when WSL is there; asks "Run Hive on Windows?" first) both use it.
- **Separate data.** Each mode is its own service with its own data folder, so projects, spaces and settings are kept per mode (no migration).
- **UI.** The status bar shows "Windows" in native mode (title "Service connection"); the connection dialog drops "in WSL" and stops the old service with `taskkill /F /IM hive.exe` instead of `pkill`.
- **Bundle.** The Windows installer carries the Linux `hive` and `hive.exe` (`tauri.release.conf.json`); `release.yml` and ci.yml's `windows` job build `hive.exe` on the Windows runner (static CRT), and ci.yml uploads the installer (`hive-windows`, 7 days, no updater artifacts).

### Claude Code on native Windows (spike, 12.5.2)
From Anthropic's documentation (code.claude.com/docs: hooks, statusline, settings, env-vars, setup; 2026-09-28), for 12.5.5:

- **Hooks, exec form** (`args` set, which `hive-hooks.json` uses): no shell on any platform. `command` is resolved as an executable (a bare name on `PATH`, or a path) and spawned directly with `args` as the argument vector, each element one argument exactly as written. An absolute path with spaces such as `C:\Program Files\nodejs\node.exe` is one valid executable (no quoting, backslashes kept). On Windows `command` must be a real executable (`.exe`): `.cmd`/`.bat` shims cannot be spawned without a shell. So `"command": "<...>\\hive.exe", "args": ["hook", "<Event>"]` works as is, and the `claude` wrapper must be an `.exe` (as planned: a copy of `hive.exe` named `claude.exe`). The `shell` field is ignored with `args`.
- **Hooks, shell form** (no `args`): `sh -c` on macOS and Linux; on Windows Git Bash when Git for Windows is installed (found automatically, or `CLAUDE_CODE_GIT_BASH_PATH`, which must name `bash.exe`/`sh.exe`), else PowerShell; `"shell": "bash"` or `"powershell"` chooses. PowerShell is started with `-ExecutionPolicy Bypass` unless `CLAUDE_CODE_POWERSHELL_RESPECT_EXECUTION_POLICY=1`.
- **`statusLine`**: only a shell `command` (no `args`, no exec form, no `shell` field). On Windows it runs through Git Bash when installed, else PowerShell. Git Bash eats unquoted backslashes, so the docs write paths with forward slashes (`~` also expands to the Windows home). Hive's current `'<hive>' statusline` (sh single quotes) works in Git Bash, even with backslashes and spaces, but not in PowerShell, where a quoted path followed by a word is a parse error (it needs `& '<path>' statusline`, which bash refuses). A form both accept: forward slashes and no character that needs quoting; for a path with spaces (a user name with a space), its 8.3 short name (`GetShortPathNameW`, when the volume has them), else the form of the shell Claude Code will pick (Git Bash found: sh quoting; else `& '...'`). When `hive statusline` runs the user's own statusline on Windows, it must use that same shell choice.
- **Environment**: hook and statusline processes inherit Claude Code's environment (so `HIVE_TERMINAL_ID` from a Hive terminal reaches them), plus `CLAUDE_PROJECT_DIR` for every hook (and `CLAUDE_ENV_FILE` for some events). `CLAUDE_CONFIG_DIR` is not set by Claude Code: it is inherited when the user or Hive set it; without it the config folder is `%USERPROFILE%\.claude` (settings in `%USERPROFILE%\.claude\settings.json`). The input's paths (`cwd`, `transcript_path`) are Windows paths.

### Claude Code on native Windows (12.5.5)
Hooks, the `claude` wrapper and the statusline, built on the spike above (`hive::windows::claude`):

- **Copies in the bin folder.** The bridge copies the running `hive.exe` (the installed one, or `HIVE_BRIDGE`'s) to `%LOCALAPPDATA%\hive\bin\hive.exe` and starts the service from that copy; the service's `wrapper::install` copies itself to `bin\hive.exe` again when it runs from elsewhere (a hand-started daemon) and to `bin\claude.exe`. So nothing Hive runs for long, the service, its hooks or its statusline, keeps the installed `hive.exe` busy, and the app's installer can replace it (the bridge itself ends with the app). A copy is made beside the file (`<name>.<pid>-<ns>.tmp`) and renamed over it; a program running from the file cannot be replaced but can be renamed, so it is first moved aside (`<name>.<pid>-<ns>.old`). Each install removes what was moved aside earlier, unless it still runs (then the next one tries again).
- **Hooks.** `hive-hooks.json` runs `bin\hive.exe` in exec form (a real `.exe`, no shell), as on Unix.
- **The wrapper** is `bin\claude.exe`, first on the terminals' `PATH`: `hive` started under the name `claude` (its own file's, `current_exe`) is the wrapper instead of the CLI. It looks for the real `claude` on its `PATH` as `wrapper::real_claude` does (below), outside its own folder, however that folder is written (compared resolved); none: "hive: no claude found in PATH", exit 127. Unless `HIVE_WRAPPED` is 1 (a `claude` started from inside a hooked one: its hooks are in place already, so it runs as it is), it sets `HIVE_WRAPPED=1` and passes `--settings <data>\hive-hooks.json` before the user's arguments. The real `claude` inherits its streams; the wrapper waits and exits with its code (126 when it cannot start; a code over 255, such as the `NTSTATUS` of a program ended by Ctrl+C, is 1), returned from `main`: `process::exit` is `ExitProcess` on Windows, which skips what runs at exit (the coverage profile). A console's Ctrl+C and Ctrl+Break reach every program on it: the wrapper handles both by doing nothing (a handler, not the inherited ignore flag), so `claude` decides and the wrapper outlives it.
- **The real `claude`** (`wrapper::real_claude`, also Diagnostics): each absolute `PATH` folder but the bin folder, `claude` with each extension of `PATHEXT` in its order (else `.COM;.EXE;.BAT;.CMD`), the first file found. The native installer's is `%USERPROFILE%\.local\bin\claude.exe`; an npm install is `claude.cmd`, which runs `node.exe` (`std::process::Command` runs a `.cmd` through `cmd.exe`, quoting its arguments).
- **What the unhooked-`claude` watcher sees** (processes named `claude`, from the terminal jobs): a native `claude.exe`, and the wrapper `claude.exe` itself while it waits, so a `claude` started through the wrapper is seen whatever its install. An npm `claude` is `node.exe` running Claude Code's `cli.js`, which the watcher also counts as `claude` (12.5.6a, `conpty::comm`).
- **The user's `PATH`** (`wrapper::user_path`) is the service's own (inherited from the app, the user's: no shell is asked), then `%USERPROFILE%\.local\bin` and `%USERPROFILE%\.claude\local`.
- **The Claude folder** is `CLAUDE_CONFIG_DIR`, else `%USERPROFILE%\.claude` (`sessions::claude_dir`, `sessions::root`: the home is `dirs::HOME`, `USERPROFILE` on Windows, never Git Bash's `HOME`).
- **`hive worktree hook-create`/`hook-remove`** run as on Unix (paths with `\`, 12.5.6b), reached from the fake `claude`'s hooks in the Windows integration test.
- **`statusLine` command** (`statusline_command`): the `bin\hive.exe` path with `/` between names and ` statusline` after it, bare when every character is a letter, a digit or one of `/._:-~` (so both Git Bash and PowerShell read it as one word); else its 8.3 short name (`GetShortPathNameW`) when that one is bare (a user name with a space); else quoted for the shell Claude Code will pick, as the service sees it: `'…'` (sh quoting) when Git Bash is found, else `& '…'` (PowerShell, `'` doubled).
- **The statusline's shell** (`statusline_shell`), for the user's own statusline, as Claude Code picks it: Git Bash (`CLAUDE_CODE_GIT_BASH_PATH`, else the `bin\bash.exe` of the first `git.exe` on `PATH`, as for terminals) with `-c`, else PowerShell (`pwsh` when on `PATH`, else Windows PowerShell) with `-NoProfile -NonInteractive -ExecutionPolicy Bypass -Command`. Time and output limits as on Unix. It joins a `windows::Job` (12.5.6a) right after it starts (`statusline_job`; one it cannot join is killed), dropped as its run ends: late or in time, it and whatever it started end then (unlike Unix, nothing it leaves in the background stays), and when Claude Code cancels a run by killing `hive statusline` (no signal on Windows), the job goes with it. A `taskkill /T` would miss the process Git Bash is forking at that moment, which then waits 5 minutes holding the output pipe.
- **Tested** on the Windows runner: `windows::claude`'s unit tests (the copies moved aside while running, the command, the short name, the shell, the wrapper against a `claude.cmd`), `statusline`'s tests through Git Bash, and the integration test: `tests/fixtures/fake_claude.rs` (never the real `claude`; std only, built by the test with `rustc`, since `cargo llvm-cov` builds no examples) as a `claude.exe` behind the wrapper gets `--settings`, its `SessionStart` hook reaches the app as an agent, its `WorktreeCreate`/`WorktreeRemove` hooks make and remove a worktree; the `statusLine` command run by PowerShell and by Git Bash prints the user's statusline and reports the window; Git Bash puts the bin folder first after the user's `.bash_profile`.

### Handshake
See [Handshake](#handshake). A refused client is not the app, so the daemon keeps waiting for one.

### Terminal open and close
1. `open_terminal` on channel n.
2. The service spawns `fish -C 'set -gx PATH <bin> $PATH'` on a new PTY. fish is the session leader, and the environment has `HIVE_TERMINAL_ID=n` and `TERM=xterm-256color`, plus, in a followed worktree, `HIVE_PORT`, `HIVE_WORKTREE_PATH` and `HIVE_ROOT_PATH` (see [Project scripts and ports](#project-scripts-and-ports-68)).
3. The service replies `terminal_opened` with the worktree it placed the cwd in.
4. A pump task copies PTY output into terminal frames. There is no scrollback on the service side. Typing and output never wait for another task (9.13): input goes through a per-terminal queue found under a short std lock, and the pump records the time of the last output in an atomic shared with the registry, so neither waits while agents are placed or their logs read. The pump waits only for the app's acknowledgements of its own output (`terminal::Output`, a count shared with `ack` through a `watch`, found under the same std lock as the input queue; see Flow control in [Wire protocol](#wire-protocol)); input never waits for them.
5. When fish exits, the pump ends the terminal's other process groups as on `close_terminal` and sends `terminal_exited {code}`. If another process keeps the PTY open (a disowned job, a `setsid` child), the output still gets 200 ms first (9.15).
6. `close_terminal` ends the terminal's session (see below). The exit is reported by the pump.

### Hook event
1. Claude Code, started through the wrapper with `--settings <data>/hive/hive-hooks.json`, runs `<abs path>/hive hook <Event>` in exec form with a 1 s timeout.
2. `hive hook` stamps `sent_ns` (`CLOCK_MONOTONIC`, before reading anything), then reads stdin: at most 512 KiB, invalid JSON kept as a string.
3. If `--record` is given, it appends a JSONL line.
4. It connects and sends `hello` and `hook` within 200 ms. It prints nothing and exits 0.
5. The service translates the call with the `ClaudeCode` adapter. A `SessionStart` marks the terminal's `claude` as hooked.
6. Agents (see [Agent detection](#agent-detection)) are updated.
7. The service closes the hook connection. Nothing of the event itself goes to the app.

### Badge (6.12)
1. `hive badge <text…>` (words joined with spaces) or `hive badge --clear` reads `HIVE_TERMINAL_ID` (a number from 1; otherwise an error and exit 2).
2. It connects, sends `hello` (role `hook`) and `badge {text}` on channel `HIVE_TERMINAL_ID` within 200 ms; on failure it prints `hive: cannot reach the Hive service: …` and exits 1.
3. The service cleans the text (control and invisible characters dropped, trimmed, at most 40 characters) and forwards `badge` to the app on that channel if the terminal is open.
4. The app shows a non-empty label as a muted pill on the terminal's tab and on its agent's row; `terminal_exited` clears it.

### Session usage (12.1)
1. `hive-hooks.json` sets `statusLine` to `'<abs path>/hive' statusline` (a shell command, as Claude Code runs a statusline; on Windows a form Git Bash and PowerShell both read, see [Claude Code on native Windows (12.5.5)](#claude-code-on-native-windows-1255)). `--settings` outranks the user's and the project's settings, so it replaces their `statusLine` in Hive's terminals only; managed settings still outrank it.
2. `hive statusline` reads Claude Code's JSON on stdin (untrusted; at most 512 KiB parsed, as a hook's). Its key is the Claude config folder it runs with: `$CLAUDE_CONFIG_DIR`, else `$HOME/.claude` (`%USERPROFILE%\.claude` on Windows; `sessions::claude_dir`, written one way: an explicit `~/.claude` is the same key). With a whole `rate_limits.five_hour` (`used_percentage` a number, rounded into 0–100; `resets_at` whole seconds), it sends `hello` (role `hook`) and `statusline_usage` within 200 ms, errors ignored.
3. At the same time it runs the user's own statusline: `statusLine.command` (with `type: "command"`) from `.claude/settings.local.json`, else `.claude/settings.json` under the input's `workspace.project_dir` (else its `cwd`, else the process's folder), else the config folder's `settings.json`. It runs with `sh -c` (on Windows the shell Claude Code picks: Git Bash, else PowerShell), in the same folder and environment plus `HIVE_STATUSLINE=1`, gets the same input (all of it, even past the parse limit) and has 10 s; its stdout is printed unchanged (nothing when over 64 KiB or late) and its exit code is Hive's (1 after a signal). With no user statusline, or when `HIVE_STATUSLINE` is set (a statusline that runs Hive's own), it prints nothing and exits 0. It runs in its own process group: late, or cancelled by a SIGTERM (Claude Code cancelling a run, which then prints nothing), the group is killed (on Windows its job, see 12.5.5); one that ended in time keeps what it left in the background. Settings files that are not regular files (a FIFO, a device) are never opened.
4. The service keeps the latest window per folder, in memory only (not persisted). The current account is the one selected in the status bar (`claude.account`, see [Claude accounts](#claude-accounts-122)), else the one the service's terminals get (`State::account`, the one place it is chosen). It sends `session_usage` when the current account's window differs from the one the app has: after a report, every second (its `resets_at` passed: null; an account switch), and to a new app.
5. The status bar shows "Session N% · resets HH:MM" (local time) while there is a window, nothing otherwise. It updates only while a `claude` runs in a Hive terminal: a chat or a `claude` outside Hive feeds nothing.

### Agent detection
1. A `SessionStart` with a `session_id`, no `agent_id` (a subagent belongs to its agent, see [Agent states](#agent-states)) and a `HIVE_TERMINAL_ID` naming an open terminal registers the agent: session id → terminal.
2. The service places it by the payload's `cwd`, never the terminal's (#19): the followed worktree whose path contains `cwd`, by whole path components, the deepest one winning (Claude worktrees live inside the main one). Placement runs git (`projects.list()`) on a blocking thread, and is done once; a project followed later does not move an agent already detected.
3. It sends `agent_detected` on the terminal's channel. The agents lock is held while placing, so a `SessionEnd` or the terminal's exit arriving meanwhile is handled after the announcement (other terminals are not blocked). An agent outside every followed project is sent with a null `project` and `worktree`; the UI does not show it.
4. A `SessionEnd` for that session (after its `agent_state` `ended`), or the terminal's exit, removes it with `agent_removed`. A `/clear` is a `SessionEnd` plus a `SessionStart` with a new session id, in either order.
5. Channel n messages go through the app's Rust side like other terminal messages, so a reloaded UI never sees agents of terminals it did not open. On `disconnected` the UI drops every agent.
6. The sidebar shows each agent as a "Claude" row (idle icon) under its worktree; clicking it shows its terminal's tab (`activateTab`).

### Agent states
`hive::states`, from `docs/hive.md` "Mapeamento de estados". The UI only renders `agent_state`.
1. A detected agent starts idle. Each later hook event with its `session_id` sets the state of the agent, or of the subagent named by `agent_id`: `SessionStart` idle; `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `PostToolUseFailure` (never error), `SubagentStart`, `PreCompact` and `Notification` `elicitation_complete`/`elicitation_response`/`quota_auto_resume_fired` working; `PermissionRequest` and `Notification` `permission_prompt` waiting for permission; `PreToolUse`/`PermissionRequest` of `AskUserQuestion`, `Elicitation` and `Notification` `elicitation_dialog`/`elicitation_url_dialog`/`agent_needs_input` waiting for your answer; `PreToolUse`/`PermissionRequest` of `ExitPlanMode` waiting for plan approval; `Stop` and `Notification` `idle_prompt`/`quota_auto_resume_stale`/`quota_auto_resume_disabled` waiting for you; `StopFailure` error; `SessionEnd` ended. `Notification` `permission_prompt` (Claude Code's reminder ~6 s into any dialog) leaves waiting for your answer or plan approval as it is. Anything else leaves the state as it is.
   - Compaction: the agent's own `PreCompact` shows working with the activity "Compacting" and remembers its state and activity; its `PostCompact` gives them back (another event in between forgets them). The `SessionStart` with `source: "compact"` of a detected session leaves the agent as it is (state, subagents, tokens); any other `SessionStart` of it detects it again.
   - A `Stop` whose `background_tasks` is not empty keeps waiting for you with the activity "N background tasks"; a `UserPromptSubmit` clears the activity.
   - Order (9.17): each hook call comes on its own connection, so a large payload still being read can arrive after a later call. The agent keeps the last `sent_ns` applied to itself and to each live subagent (dropped when the subagent leaves); an event of the same one with an older `sent_ns` changes neither its state nor its activity (nor wakes a subagent waiting on a background task), but is still forwarded and still counts for its worktree, its background launches, a subagent leaving and the silence timer. An equal `sent_ns` applies.
2. A subagent joins the list on its first event with a state and leaves it on `SubagentStop` (or a `SessionEnd` carrying its `agent_id`), unless it ended its turn to wait on a background task it launched: the task ids come from its `PostToolUse` `tool_response` (`backgroundTaskId` for Bash `run_in_background`, `taskId` for `Monitor`, `agentId` for `Agent`), and Claude Code lists the session's running ones as `background_tasks` on every `Stop`/`SubagentStop`. While one of its launches is in that list it stays listed as working (silence does not change it) until it is woken (`SubagentStart` again); it leaves when a later list has none of them, when its own worktree is removed, or with its agent. At most 32 are kept per agent, and ids or types over 256 bytes are ignored, so a message always fits in a frame.
3. Rule 1: `state` is the most urgent of the agent's own state, its subagents' states and "with subagents" when any subagent is live. Urgency, highest first: `waiting_permission`, `waiting_plan`, `waiting_answer`, `error`, `waiting_you`, `with_subagents`, `working`, `idle`, `ended`.
4. Rule 2 (interrupts; Esc/Ctrl+C fire no `Stop`, nor does declining a dialog): every second (the unhooked-claude tick) the service reads the new lines of the transcript of each agent that is working, with subagents or on a dialog (`transcript::Usage`, the same bounded reader as its tokens; the lines already there when the agent was detected are read first and never count). When the last main-conversation message read is `[Request interrupted by user…]` or a declined tool call (Claude Code's `toolUseResult` "User rejected tool use" on a record with a failed `tool_result`; declining with feedback writes another marker and Claude goes on; the result's text is the tool's, so it is never trusted), the agent and each subagent working or on a dialog (not those waiting on a background task) go to waiting for you, `interrupted` and not pending, until the displayed state changes. Fallback: when its terminal has printed nothing for `agents.silence_secs` (5 s by default, see [Settings](#settings)), counted from the later of the last output and the last hook event, the agent and each subagent that is working go to waiting for you. The three dialog states never decay with silence (a dialog is static on screen). Output alone never moves a state back; only hook events do.
5. Pending (the "N pending" counter and F8): waiting for permission, a plan or an answer, error and waiting for you. `urgency` is the state's rank in the order above; the app shows a collapsed project or worktree with the state of highest `urgency` inside and counts agents with `pending`, so it keeps no table of its own. Except (hive.md item 5): an agent whose displayed state goes from working or with subagents to waiting for you while its terminal is the one in `view` and the window has the focus is seen, so not pending, until its displayed state changes again (looking away later keeps it seen).
6. `agent_state` is sent on the agent's terminal channel only when the message changes.
7. A subagent's own worktree (#22), sent as its `worktree` (the worktree's id, i.e. its path). Linked by a `worktree_created` carrying the subagent's `agent_id` (the path the hook created), or else by the subagent's own events: the first time each new `cwd` of a subagent without a worktree is seen, the service places it like an agent (`projects::place`, git on a blocking thread) and links the worktree found when it is not the agent's own. Only when the agent itself was placed; paths over 4096 bytes are ignored. A `worktree_removed` of that path unlinks it; the subagent leaving drops it. The sidebar gives that worktree no row (9.35), its path is the subagent line's tooltip, unless an agent runs in it or a terminal of the human's opened in it (the worktree `projects::place` gave the terminal at `open_terminal`, until it exits): `subagent_worktrees` lists those it hides. To confirm by spike 1.12: whether `WorktreeCreate` carries `agent_id`, and that a subagent's `cwd` is its worktree.
8. Activity and time: an event with an `activity` sets it for the agent, or for the subagent that fired it; `Stop`, `StopFailure`, `SessionEnd` and (for a subagent) `SubagentStop` clear it, and so does rule 2 for the agent or subagent it interrupts. `since_ms` is when the displayed state (a subagent's: its own state) last changed, on the wall clock: the daemon gives each agent the wall time it was detected and later times are counted from it with the monotonic clock. The sidebar shows the time in the state ("12s", "3m", "1h", from `since_ms`, one shared 1 s timer) and the activity, muted, after the state's name.
9. Subagents in the sidebar (9.35): each live subagent is one line under its agent, smaller and dimmer than an agent row: its state's icon (same colour and shape, smaller), its `agent_type`, its activity (cut with an ellipsis) and the time in its state. The line is not a control: nothing to click, select or focus, no hover state and no context menu. There is no subagent conversation view (6.10 was dropped).

### Transcripts
1. The agent's `SessionStart` `transcript_path` is kept on its `states::Agent` (`transcript`) when it is an absolute `.jsonl` path of at most 4096 bytes; its tokens (6.9) and interrupts (rule 2) are read from there.
2. Each read canonicalizes it (links resolved) and reads it only when it is a regular file inside a Claude projects folder: its terminal's account's, the default one's (`$CLAUDE_CONFIG_DIR/projects`, else `~/.claude/projects`) or any other account's (12.2, see [Claude accounts](#claude-accounts-122)).
3. The first read takes the last 8 MiB (a line cut at the start does not parse and is skipped), then each read takes the whole lines added since (a line still being written waits; a transcript that shrank is read again from its start).

### Tokens and context (6.9)
From the transcripts only: no 5 h or weekly limits, and the user's statusline is never touched.
1. An agent's `PostToolUse`, `Stop` or `SubagentStop` (its subagents' too) marks its usage due; the next tick of the unhooked-claude timer (every second) reads the whole lines its transcript (`transcript_path`, checks and 8 MiB bounds in [Transcripts](#transcripts)) gained since the last read. So a transcript is read at most once a second per agent, and only the last 8 MiB of a long one count at first.
2. Each `assistant` record outside a sidechain with a `message.usage` counts: the context is its `input_tokens + cache_creation_input_tokens + cache_read_input_tokens` (records with no context, such as API errors, are skipped); `output_tokens` add up, once per `message.id` (Claude repeats a message's usage on each of its content blocks; the last one wins). A field that is missing, not a number or over 100 million counts as 0.
3. The context window (8.1): 1M when the transcript's model (`message.model` of the last counted record, at most 128 bytes) ends in `[1m]` or starts with `claude-opus-5`, `claude-sonnet-5`, `claude-fable-5` or `claude-mythos-5`; else 200k. Whatever it is, at least 1M once the context passed 200k. The transcript never carries the `[1m]` suffix and the hooks and `<Claude config folder>/sessions/<pid>.json` carry no model (Claude Code 2.1.283), so an agent on a 4.x model asked for as `[1m]` shows 200k until its context passed 200k.
4. `agent_usage` is sent on the agent's channel when context, window or output changed. The sidebar shows "ctx 42%" after the agent's state line (rounded down).
5. Sessions panel: `sessions` entries carry `context_tokens` and `output_tokens`, counted the same way while summarizing the log (cached with the summary).
6. Sessions panel, `running` (8.16): a session runs only when a `claude` is known to run its id: the agents of Hive's terminals (their hooks name the session), and each process named `claude`, from, in order, Claude's own record `<Claude config folder>/sessions/<pid>.json` (its `sessionId`, when its `pid` is that process's), its arguments in `/proc/<pid>/cmdline` (`--session-id <id>`, else `--resume`/`-r <id>` without `--fork-session`), or an open `<id>.jsonl` in `/proc/<pid>/fd`. Ids must be UUIDs; the record and the command line are read up to 64 KiB, at most 4096 open files per process. A process none of these name (a bare `claude`, `--continue`) marks nothing. On macOS only the record is read. The app shows a session of its own terminal as "Show its terminal"; one running outside Hive has Resume and Delete disabled, without text, and "Continue in New Session" enabled.
7. Sessions panel, reading the logs (9.12): each log is read once. The service keeps, per log, how far it read (the end of its last whole line) and the summary so far; a log that grew is read from there, one that shrank or has another inode from its start, one whose inode, size and modification time are unchanged not at all. A last line without its newline counts in the summary and is read again once whole. The same summaries serve the list, `locate_session`, `delete_session` and the agents' names. The list takes the logs by modification time and reads only as many as it lists (500, plus one to tell `truncated`).

### App disconnect (or SIGTERM)
1. The accept loop stops and the watcher stops.
2. For every terminal, every process group in its PTY session gets SIGHUP.
3. The service waits until no process in those sessions is alive, for at most 2 s, then sends SIGKILL to what is left.
4. The socket is removed and the daemon exits 0.

fish job control puts each job in its own process group, which is why the service ends the groups of the whole session and not only fish's group. Processes that left the session with `setsid` or `nohup` survive (risk 9).

### The user's `claude`
Diagnostics names the `claude` the wrapper would run (`wrapper::real_claude` on the user's `PATH`). The user's `PATH` (`wrapper::user_path`) is the one their terminals get, since the service started through `wsl.exe` lacks what their shell config adds (e.g. `~/.local/bin`): the service runs the terminals' shell once (`fish -c` on WSL, `$SHELL -l -c` on macOS; none on native Windows, where the service's own `PATH` is the user's) with a fixed `printf '%s\n' "$PATH"`, stdin and stderr closed, and takes the last line it prints when it exits successfully within 5 s after at most 64 KiB (else the service's own `PATH`), then appends `~/.local/bin` and `~/.claude/local`, where Claude Code installs itself; empty entries are dropped. It is asked for in the background the first time it is needed, never at start (9.20): Diagnostics and `gh` (a space's GitHub account, the pull requests and Actions views) wait for that answer. It is asked again, in the background, whenever no `claude` is found on it.

### Unhooked claude
1. Every 1 s the watcher lists `/proc`.
2. A terminal whose session contains a process named `claude`, with no `SessionStart` from that terminal for 5 s, gets one `unhooked_agent`.
3. The state resets when that `claude` exits.

### Worktree create (CLI and `WorktreeCreate` hook mode)
1. Find the main repository root, even from inside a linked worktree: the first entry of `git worktree list --porcelain -z`. A bare repository is refused.
2. Validate the name with `^[a-z0-9][a-z0-9._-]*$`, the same rule as the UI. Refuse an existing directory. An existing `worktree-<name>` branch is refused by git itself, and a `--base` starting with `-` is refused.
3. Collect the `.worktreeinclude` files before creating anything. `git ls-files --others --ignored --exclude-from=.worktreeinclude` finds the matches and `git check-ignore` keeps only the gitignored ones.
4. Run `git worktree add -b worktree-<name> .claude/worktrees/<name> <base>`. The base is a local or remote branch, or HEAD.
5. Copy the included regular files. Existing paths are never overwritten and symlinks are never followed.
6. Print only the path. In hook mode, any failure exits non-zero with an empty stdout.

`create` returns the path and its notes, which the CLI prints on stderr as `hive: <note>` and the service sends to the app: a warning when the project has its own `WorktreeCreate` hook in `.claude/settings{,.local}.json`, and how many `.worktreeinclude` files were copied. `remove` and `hook-remove` run `git worktree remove` without `--force` and keep the branch. `hook-remove` only removes paths directly under `<repo>/.claude/worktrees/`. Both hooks are registered in `hive-hooks.json` (see below).

### Worktree hooks
1. Claude Code, through the wrapper's settings, runs `<abs path>/hive worktree hook-create` for `WorktreeCreate` (60 s timeout: `git worktree add` plus the `.worktreeinclude` copy) and `hive worktree hook-remove` for `WorktreeRemove` (10 s timeout), in exec form. The hook input is at most 64 KiB.
2. Each does its work as above. Only on success, it then forwards the call to the service like `hive hook` (same `hello` + `hook`, 200 ms, `HIVE_TERMINAL_ID`), as event `WorktreeCreate` with the created path added as `worktree_path`, or `WorktreeRemove` unchanged. Forwarding never changes stdout nor the exit code.
3. The `ClaudeCode` adapter maps them to `worktree_created {name, path}` and `worktree_removed {path}`, keeping `session_id`, `cwd` and `agent_id`/`agent_type` (a subagent's worktree). They do not change agent states.
4. On either one the service lists the projects again off the frame loop and sends `projects`, so a `claude -w` or subagent worktree appears, and a removed one disappears, without "Refresh worktrees". It does so after updating the agent states, so `projects` follows any `agent_state` the call caused. Any other `git worktree add/remove/prune` (an agent's Bash, `hive worktree remove`, a terminal outside Hive) reaches the app through `hive::registry`. `State::worktrees_changed` is the single point for both: it sends `projects` only when some project's worktrees differ from what the app was last sent (every reply carrying projects records them), and runs in turn with the app's own create and remove (and with `list_projects`, `add_project` and `remove_project`, so a list it made earlier never follows theirs), so each change reaches the app once. A worktree folder deleted by hand leaves git's registry alone: it disappears on the next list (git marks it prunable, and prunable worktrees are hidden).
5. The store replaces its list on every `projects`. A selected worktree that is no longer listed leaves its project selected (nothing, if the project went too), and `worktree:<id>` collapsed keys of unlisted worktrees are dropped. Its terminal tabs stay open. An agent placed in it keeps its `worktree` id, so, like an agent outside every project, it is no longer shown in the tree but still counts as pending and F8 still reaches its tab.

### Load test (1.11, #28)

`e2e/load.e2e.ts` (Playwright project `load`, run after the other specs, alone) opens 20 terminals with `?mock=load`: the mock replays a recording into each one through the real path (transport `onData` → terminal manager → xterm.js), at recorded timing, starting 0.5 s after the terminal opens plus 100 ms per terminal id. After a 3 s warm-up it types into the focused terminal for 12 s (10 keys/s) and measures:
- **input latency**: key `timeStamp` → the echo parsed (the mock appends `OSC 7777` to every echo in this mode) → the next animation frame;
- **frames**: every `requestAnimationFrame` interval; **long tasks**: `PerformanceObserver("longtask")`;
- **dropped output**: after the replays end, every hidden terminal's buffer must equal a fresh xterm of the same size fed the whole recording at once.

Pass: input p95 < 50 ms (typing starts to feel laggy past ~50 ms; native terminals sit at 10–40 ms) and p99 < 100 ms (RAIL response budget), frame p95 < 33.3 ms (30 fps), no long task ≥ 100 ms, nothing dropped. Results go to `target/e2e/load.json`.

**Recording.** `src/transport/replay.ts` generates a deterministic ~19 s Claude Code-like session: three turns of prompt, spinner with shimmer (one truecolor per character) + todo list + input box redrawn at 12.5 Hz the way Ink does it (DEC 2026 synchronized output, erase-line + cursor-up over the whole dynamic region), streamed answer redrawn every 33 ms, and an 80-line diff with truecolor backgrounds flushed in 4 KiB chunks. 449 KB, ~23 KB/s per terminal, ~460 KB/s for 20. To use a real capture instead, record one with asciinema (v2 or v3 cast, `asciinema rec --command claude target/claude.cast`), put it under the repo so Vite serves it, and run with `HIVE_LOAD_CAST=/target/claude.cast` (or open `/?mock=load&cast=/target/claude.cast`); only output events are replayed, and the end-of-recording check is skipped.

**GPU.** The spec launches Chromium with ANGLE on the system GL (`--use-gl=angle --use-angle=gl`), and inside WSL sets `GALLIUM_DRIVER=d3d12` with `/usr/lib/wsl/lib`, so WebGL runs on the Windows GPU. Chromium's default SwiftShader saturates the main thread with a single replaying terminal (~11 fps) and says nothing about a real GPU; Mesa's llvmpipe (no GPU) competes with the page for CPU and fails the thresholds.

**Result (2026-09-23, Chromium headless on Linux/WSL2, Intel Iris Xe through D3D12, machine otherwise idle, three runs):** input p50 28.5–30.3 ms, p95 36.4–38.0 ms, p99 38.1–43.9 ms, max 39–64 ms; frame p50 and p95 16.7 ms (60 fps), max 33–117 ms; no long task; nothing dropped. Inside the full `bun run e2e`: p95 38.7 ms, p99 62.5 ms, max 175 ms. **Pass.** While another agent was compiling Rust (load average 8–16 on 12 cores) the same test failed (input p95 70–1400 ms, with stalls of 0.4–2 s that had no long task, so outside the page), so timings are only meaningful on a quiet machine.

**Waste found (not fixed):** a hidden terminal loses its WebGL addon and xterm.js falls back to its DOM renderer. On every scroll xterm refreshes the selection, and `RenderService.handleSelectionChanged` makes the DOM renderer rebuild every row even though rendering is paused; in a `display: none` pane each glyph width measures 0, is never cached, and is measured again (`WidthCache._measure`, a forced layout). With 20 terminals this was ~35% of the main thread in a CPU profile. It still passes, but it is margin lost on slower machines; disabling that call for hidden terminals (xterm internals) removed it entirely in an experiment.

**This is not WebView2 on Windows.** To re-run in the real app: start it with `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9222` and point the spec at it with Playwright's `chromium.connectOverCDP("http://localhost:9222")` after navigating the window to `?mock=load` (the transport honours `?mock` inside Tauri); or, by hand, open `?mock=load` in the debug build's DevTools and run the same probes.

### Windows app during development

The code and every build stay in WSL (TODO 1.0, human decision 2026-09-23). `scripts/win-dev.sh`:
1. cross-compiles `hive-app` for `x86_64-pc-windows-msvc` with `cargo xwin`, with a static CRT because a stock Windows has no VC++ redistributable;
2. copies the `.exe` to `%LOCALAPPDATA%\hive-dev`;
3. builds `target/debug/hive` and exports `HIVE_BRIDGE` (that path) and `HIVE_WSL_DISTRO` through `WSLENV`, so the app's bridge runs the development build;

5. opens the app through PowerShell, because launching a Windows `.exe` straight from WSL interop fails.
